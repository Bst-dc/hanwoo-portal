### 왜 브라우저에서 API를 직접 부르지 않는가 (바꾸지 말 것)

2026-10-05에 실제로 확인한 사실:

| 확인 항목 | 결과 | 의미 |
|---|---|---|
| https 접속 | 안 됨(타임아웃) | https인 GitHub Pages에서 http 호출은 브라우저가 차단 |
| `Access-Control-Allow-Origin` | 없음 | 다른 출처의 fetch를 브라우저가 차단 |

## 4. 데이터 원천 (API)

- 서비스: 공공데이터포털 `[운영계정]축산물품질평가원_축산물등급판정정보`
- 기능: `auct/cattlePriceDetail` (축산물 소도체 경락상세정보)
- 주소: `http://data.ekape.or.kr/openapi-data/service/user/grade/auct/cattlePriceDetail` (http만 됨)
- 요청: `serviceKey`, `abattCode`, `startYmd`, `endYmd`, `breedCd=024001`(한우), `sexCd`, `defectIncludeYn=Y`(결함포함가격)
- 코드: 음성 `0513`, 고령 `0905`, 부경 `0202` / 거세 `025003`, 암 `025001`
- 응답: XML. 등급별 `auctAmt`(원/kg 평균 경락단가), `auctCnt`(두수), `min/maxAuctAmt`, `weight`, `sumWeight`, `sumAuctAmt`

### 실제 응답에서 확인한 특성 (모두 코드에 반영됨)

1. **거래가 없으면 0이 아니라 항목 자체가 빠진다.** `<auctAmt>` 등이 없는 행이 온다. 0으로 채우면 "0원"이 표시되는 조용한 실패가 생긴다.
2. **휴장일도 오류가 아니다.** 결과코드는 `00`이고, 행은 있으나 모든 행에 두수가 없다.
3. **한 응답에 여러 집계가 섞여 있다.** `gradeType`이 A는 세부등급(1++A 등, **위젯이 쓰는 것**), B는 육질등급 합계, C는 육량등급 합계, D·E·F는 결함제외·등외제외·평균 계다.
4. **`gradeCd`와 `gradeNm`이 다르다**(예: 1++A의 코드가 `0A`, 3C의 코드가 `4C`). 그래서 `gradeNm`으로 거른다.
5. **기간을 넣으면 날짜별이 아니라 합산 1줄로 온다.** 그래서 하루씩 호출한다.
6. **코드를 잘못 넣어도 오류가 아니라 입력값이 그대로 되돌아온다**(가이드에 명시). 그래서 응답의 `judgeBreedNm`, `judgeSexNm`, `startYmd`를 요청과 대조한다.
7. **키 오류도 HTTP 200으로 온다.** 본문의 `resultCode=99 등록되지 않은 서비스키`로만 알 수 있다.
8. **정합성 확인:** 평균도체중×두수=거래중량, 평균가×거래중량≈거래대금이 성립한다. 1++B와 1++C의 가중평균도 B유형 "1++" 행과 정확히 일치했다.

## 5. `data/hanwoo_7d.json` 형식

```json
{
 "dummy": false,
 "source": "축산물품질평가원 ... (결함포함가격)",
 "generatedAt": "2026-10-05T18:07:41+09:00",
 "dates": ["20260915", "...", "20261005"],
 "markets": [{"code": "0513", "name": "음성"}, ...],
 "sexes": [{"code": "025003", "name": "거세"}, {"code": "025001", "name": "암소"}],
 "grades": ["1++A", "1++B", "1++C", "1+A", ..., "3C"],
 "fetches": [
  {"date": "20261002", "market": "0513", "sex": "025003", "status": "ok",
   "grades": {"1++A": {"amt": 29268, "cnt": 55}, "3A": null, ...}}
 ]
}
```

- `fetches` 한 건은 API 호출 한 번(날짜 × 시장 × 성별)이다.
- `status`:
  - `ok`: 경매 있음
  - `closed`: 이 시장·성별에 그날 거래 없음
  - `pending`: 끝 날짜가 평일인데 세 시장 모두 휴장으로 응답함 → 업로드 전이거나 공휴일
  - `error`: 수집 실패(`error`에 이유)
- 등급 값이 `null`이면 그 등급 거래가 없다는 뜻이다(0원 아님).
- `reused: true`는 이번 호출이 실패해서 직전 파일의 값을 유지한 칸이다.

## 6. 화면 규칙

- **끝 날짜(KST 기준):** 오전 10시 전이면 오늘-2일, 10시부터는 오늘-1일. 브라우저 시간대와 무관하게 KST로 계산한다. Python의 `latest_date`도 같은 규칙이다.
- **표시 날짜:** 끝 날짜 이전에서 **경매가 있었던 최근 7일**(사용자 결정 B안). 세 시장 모두 휴장인 날만 빼고, 수집 오류가 난 날은 남겨서 "오류"로 드러낸다.
- **갱신 지연 경고:** 끝 날짜가 없거나 `pending`이면 하단에 "⚠ 날짜 시세가 아직 없습니다(갱신 대기 또는 공휴일)"를 띄운다. 평일 공휴일 다음 날에는 하루 동안 이 문구가 정상적으로 뜬다(예: 2026-10-06).
- **선택:** 시장(음성/고령/부경) × 성별(거세/암소) 버튼. 기본은 음성·거세. 표는 15등급 × 7일이고, 육질등급이 바뀌는 줄에 구분선이 있다.
- **칸 표시:**
  - 거래 있음: `29,268 (55)` = 단가(원/kg)와 괄호 안 두수
  - 2두 이하 거래: 흐리게 표시
  - `–`: 거래 없음. 그 성별만 출하가 없는 날도 여기에 포함된다.
  - `휴장`: 그 시장의 두 성별 모두 거래 없음
  - `대기`: pending 상태
  - `미수집`: 데이터 없음
  - `오류`: 수집 실패, 등급 키 누락, 0 이하 가격
- **JSON을 못 읽으면** 실패 메시지만 보여준다(가짜 숫자를 대신 보여주지 않는다).

## 7. 수집기의 안전장치

| 상황 | 동작 |
|---|---|
| 한 칸 실패 | 그 칸만 `error`. 직전 파일에 값이 있으면 그 값을 유지(`reused`) |
| 네트워크 오류, resultCode 01·02·04·05 | 최대 3회 시도(2초, 4초 대기) |
| 키 오류(99), 응답 모양 이상 | 재시도하지 않음(다시 해도 같음) |
| 연속 6건 실패 | 즉시 중단, 종료코드 1, 기존 파일 유지(틀린 키면 약 2초 만에 끝남) |
| 전체 실패 20% 초과 | 기존 파일을 덮어쓰지 않고 종료코드 1 → Actions 실패, GitHub 메일 |
| 저장 | 임시 파일에 쓴 뒤 교체(반쯤 깨진 JSON이 남지 않음) |
| 키 형식 | Encoding 키(`%2B` 등)와 Decoding 키 모두 허용(`unquote`) |

수집이 끝나면 요약을 출력한다. Actions에서는 실행 화면의 Summary에도 같은 요약이 뜬다. 요약이 잡는 이상 신호는 이렇다.

- 최근 경매일이 7일보다 적음(수집 기간 부족)
- 직전 경매일 대비 ±15% 이상 급변(양쪽 모두 3두 이상일 때만)
- 같은 날 두 시장의 단가와 두수가 똑같음(도매시장 코드 오류 의심)
- `error`, `pending`, `reused` 칸

## 9. 운영

- **비밀값:** 저장소 Settings → Secrets and variables → Actions → `EKAPE_KEY`. 키를 교체할 때도 여기만 바꾼다.
- **수동 실행:** Actions → "한우 7일 시세 갱신" → Run workflow
- **커밋:** 봇 커밋 메시지는 `한우 7일 시세 자동 갱신 YYYY-MM-DD HH:MM`이다. 사람이 push하기 전에는 `git pull --rebase`를 해서 봇 커밋과 충돌하지 않게 한다.
- **해외 접속:** GitHub 서버(해외)에서도 API 접속이 됨을 2026-10-05에 확인했다. 앞으로 막히면 연속 실패로 중단되고 사이트에는 마지막 정상 데이터가 남는다. 대안은 이 PC에서 윈도우 작업 스케줄러로 수집해 push하는 것이다.
- **반영 지연:** GitHub Pages 반영과 캐시 때문에 push 후 1~10분 늦게 보일 수 있다.

## 10. 바꾸면 안 되는 것 (불변 조건)

1. 서비스키를 `index.html`이나 `js/`처럼 공개되는 파일에 넣지 않는다.
2. 값이 없는 칸을 0으로 채우지 않는다. 표시 단계에서 `null`은 `–`, 0 이하는 `오류`다.
3. JS `endDate`와 Python `latest_date`의 10시 규칙을 함께 바꾼다. 테스트도 함께 고친다.
4. 실패 시 가짜 데이터를 보여주는 대체 표시를 다시 만들지 않는다.
5. `gradeType == "A"`와 `gradeNm`으로 거르는 방식을 유지한다(`gradeCd`로 거르면 틀린다).
6. 수집기를 바꾼 뒤에는 `scripts/fixtures`의 실제 응답 테스트가 통과해야 한다.

## 11. 알려진 한계와 미확인 사항

- **고령·부경 코드는 간접 확인만 했다.** 응답에 시장 이름이 없어서, 음성과 값·두수가 다르고 가격대가 맞는지로만 확인했다. 시장 간 동일값 경고로 계속 감시한다.
- **휴장일 fixture는 일부만 있다.** `closed_20261003_025003.xml`은 사용자가 브라우저로 본 1++B 행 하나만 옮긴 것이다. 휴장 판정은 "모든 행에 두수 없음" 규칙이라 행 수와 무관하다.
- **평일 공휴일과 업로드 지연은 구분할 수 없다.** 그래서 둘 다 `pending`으로 처리하고 하루 동안 안내 문구를 띄운다.
- **고령은 거래 두수가 적다**(하루 1~6두가 흔함). 등급 간 역전(예: 1++C가 1++B보다 비쌈)이 생길 수 있는데, 데이터 오류가 아니라 표본이 작아서다.
- **GitHub 예약 실행 정지:** 저장소에 60일간 활동이 없으면 GitHub이 예약 실행을 멈춘다. 매일 봇이 커밋하므로 사실상 해당되지 않는다.
